## Project Overview

This project has been developed for two STM32F103R6 microcontrollers and has been built using the arm-none-eabi toolchain, build tools, Eclipse CDT, the Proteus simulator and CubeMX.
The system simulates:

- Asynchronous USART communication between one STM32F103R6 microcontroller and a Virtual Terminal,

- Asynchronous USART communication between the two STM32F103R6 microcontrollers,

- the operation of an LCD display controlled by one of the microcontrollers, and

- the control of two DC motors using PWM signals generated by Timer 3 channels of the second microcontroller.

## System Architecture

- The two STM32F103R6 microcontrollers have been interconnected via USART2 on MCU1 (the first microcontroller) and USART1 on MCU2 (the second microcontroller).

- MCU1 has also been connected to a Virtual Terminal via USART1 (asynchronous mode), allowing the user to enter control commands to increase or decrease the speed of either motor.

- Two DC motors (MOTOR1 and MOTOR2) have been added in the Proteus simulation and are controlled via PWM outputs on Timer 3 channels 1 and 2 of MCU2.

- Motor speeds range from 0 to 16 units and are displayed on the LCD using a custom-defined character that represents each unit as a filled block.

## Functional Description

MCU1 receives a two-character command from the Virtual Terminal, ending with a carriage return (\r):

- The first character must be '1' or '2' to indicate the motor.
- The second character must be 'i' (increase) or 'd' (decrease) to modify the motor speed.
- e.q. 
	- '1i\r'  (acceleration of Motor 1)
	- '2d\r'  (deceleration of Motor 2)

For valid input, MCU1 constructs a command in the form of:

```c
struct MotorCommand {
	uint8_t motor;
    uint8_t velocity;
};
```

and transmits it to MCU2 via USART protocol.

MCU2 receives the command and adjusts the corresponding motor's speed accordingly using PWM.

Speed increments or decrements by one unit, staying within the range of 0–16.

If the motor is already at max (16) or min (0), further commands to increase or decrease have no effect.

The LCD display shows the current speed of each motor using custom bar characters:

- The top row represents speed of MOTOR1.

- The bottom row represents speed of MOTOR2.

## Code Structure

The following modules and functionalities have been implemented as part of this project:

- `...\cubemx1\code1`:

	- `uart_driver.h`, `uart_driver.c` - A custom driver for the USART peripheral has been implemented, supporting both transmission and reception functionalities for asynchronous communication between MCUs and between MCU and Virtuel Terminal.
	The following functions have been provided:

		- `void UART_AsyncTxString(UART_Target target, char const * string)`

		- `void UART_AsyncTxMotorCommand(UART_Target target, MotorCommand motorCommand)`

		- `char* UART_BlockRxString(UART_Target target)`

		- `MotorCommand UART_BlockRxMotorCommand(UART_Target target)`
		
	- `work.h`, `work.c` - The core logic of MCU1 has been implemented in accordance with the project requirements.
	The system continuously waits for a command to be received via the Virtual Terminal.
	Upon receiving a valid command, a MotorCommand structure is generated and sent to MCU2 to request a change in the speed of the selected motor.
	Input validation has been implemented to ensure the received string conforms to the expected format, and appropriate error messages are returned when needed.
	
- `...\cubemx2\code2`:

	- `uart_driver.h`, `uart_driver.c` - A custom driver for the USART peripheral has been implemented, supporting both transmission and reception functionalities for asynchronous communication between MCUs. It enables the reception and transmission of structured motor control data.
	The following functions have been implemented:

		- `void UART_AsyncTxMotorCommand(MotorCommand motorCommand)`

		- `MotorCommand UART_BlockRxMotorCommand()`

			
	- `work.h`, `work.c` - The core logic of MCU2 has been implemented in accordance with the project specification.
	A custom character, representing one unit of motor speed as a filled rectangle, has been defined and loaded into the CGRAM of the LCD controller.
	Based on the data received from MCU1 via USART, MCU2 determines which motor should be controlled and adjusts its speed accordingly using PWM signals.
	The current speeds of MOTOR1 and MOTOR2 (ranging from 0 to 16) have been visually represented on a 16x2 LCD display using repeated instances of the custom character.
		
		- The top row displays the speed of MOTOR1.

		- The bottom row displays the speed of MOTOR2.
		
	- `lcd.h`, `lcd.c` - The logic required to control and interface with the 16x2 LCD display has been fully implemented in this module. A 4-bit data interface has been used to communicate with the LCD, and characters have been rendered in the 5x8 dot matrix format.

The rest of the code was automatically generated using CubeMX.
	
## Required Tools

This project requires the following tools:

- **GNU MCU Eclipse IDE (version 2021-06-R)**
- **GNU ARM Toolchain (version 10.2.1)**
- **GNU MCU Build Tools (version 4.2.1-2)**

These tools can be downloaded from Google Drive:

- [Download tools.zip from Google Drive](https://drive.google.com/drive/folders/1CaS04-ndH8tqtUvtaRrHiHTAvh6bvUi4?usp=drive_link)

## Installation Steps

- Extract the archives containing the required tools.
- Add the following directories to the system's PATH environment variable:
    - **build-tools-4.2.1-2\bin**
    - **arm-none-eabi-gcc-10.2.1-1.1\bin**

## Running the Project

- **Proteus**:
	- Run as Administrator: Open Proteus with administrator rights.
    Open the provided Proteus project file.
	For each STM32F103R6 microcontroller, load the appropriate program file:
	- **MCU1**:
		- `...\build\code1.elf` or
		- `...\build\code1.hex`
	- **MCU2**:
		- `...\build\code2.elf` or
		- `...\build\code2.hex` 

- **Eclipse CDT**:
To build and run the firmware for both microcontrollers, the project must be set up twice in Eclipse CDT: once for MCU1 and once for MCU2. Perform the entire setup procedure once for cubemx1 and repeat the same steps for cubemx2. Each microcontroller has a separate project folder and must be built independently.

	- Workspace Setup: 
		- Set the workspace to the:
			- **cubemx1** folder (for MCU1)
			- **cubemx2** folder (for MCU2)
	- Toolchain Setup:
		- Navigate to **Windows -> Preferences -> Workspace -> Arm Toolchains Paths**.
        - Set the Default Toolchain to: **xPack FNU Arm Embedded GCC**
        - Set the Toolchain Folder to: `...\arm-none-eabi-gcc-10.2.1-1.1\bin`
        - Set the Build Tools Folder to: `...\build-tools-4.2.1-2\bin`
	- Importing the Project:
		- Select **Import -> C/C++ -> Existing Code as Makefile Project**.
        - Set the Existing Code Location to:
			- `...\project\cubemx1\code1` (for MCU1)
			- `...\project\cubemx2\code2` (for MCU2)
        - Select the Toolchain: **Arm Cross GCC**.
	- Project Settings:
		- Navigate to **Properties -> C/C++ Build -> Settings** and click **Apply and Close** (wait for the indexer to process paths).
		- Navigate to **Properties -> C/C++ General -> Paths and Symbols -> Symbols**  and add the following symbols as GNU C:
			- **USE_HAL_DRIVER**
			- **STM32F103x6**
	- Creating Build Targets:
		- Right-click on the project and select **Build Targets -> Create**.
		- Create the following targets: 
			- **all**
			- **clean**
	- Building the Project:
		- Double-click the **all** target to build the project.
